# 58. `scx-p21`: STEP Part 21, Part 42 data, units and product structure

As of 2026-11-27. Trust: MEASURED (tests, the pin comparison and the timings below), with the
design JUDGED. Clause numbers (§) are those of ISO 10303-21:2016 (edition 3) unless another
part is named.

## 1. What the pin has, and where it goes

The pin (solidcore 03e16c9e) keeps STEP in two crates. `solidcore-record/src/step` reads the
file and holds its contents as data; `solidcore-step` builds kernel bodies from that data and
writes bodies back out. Only the first is data with no geometry, so only it moves here.

| Pin file (`solidcore-record/src/step/`) | Lines | What it is | Goes to |
|---|---|---|---|
| `p21.rs` | 1,582 | Part 21 lexer and parser, `Exchange`, `Param`, `Entity` | `scx-p21`: `parse`, `exchange`, `text`, `error`; a writer added (`write`) |
| `units.rs` | 466 | SI and conversion-based units, a context's units and uncertainty | `scx-p21::units` |
| `protocol.rs` | 385 | AP203, AP214 or AP242 and its edition, from `FILE_SCHEMA` | `scx-p21::protocol` |
| `geom.rs` | 444 | Part 42 curves and surfaces as plain data | `scx-p21::part42` |
| `read.rs`, `read/tests.rs` | 2,271 | Part 42 entities read from an exchange | `scx-p21::part42` |
| `product.rs`, `product/tests.rs` | 1,893 | Products, representations, assembly occurrences, colours | `scx-p21::product` (section 6) |
| `model.rs` | 392 | The neutral B-rep body (frames, faces, loops, in millimetres and degrees) | `scx-step`: it is topology, not file data |
| `solidcore-step` (whole crate) | 14,801 | Bodies from the data, and bodies to STEP | `scx-step`, later |

What leaves the parser in the move:

- `Exchange::common_face_name` and the face-name helpers. They read `ADVANCED_FACE` names, which
  is what `scx-step` does with an exchange, not what an exchange is.
- `Exchange::schemas`, `originating_system`, `preprocessor` and `description` as copies stored next
  to the header. They are now read from the header's records (`Header::schemas` and
  `Header::file_name`), so there is one copy of each.
- The pin's `Exchange::duplicates`. A repeated id is now a `Warning::DuplicateId`, along with the
  other things a read tolerates.

## 2. Shape

- **Plain owned data.** There is no global state. Every call takes its `Limits` and `Progress` as
  arguments, so there is no `parse_with_max_bytes` / `parse_with_budget` family.
- **Lossless.** `parse(write(x)) == x` for every exchange that `write` accepts. Keeping that true
  means the model keeps everything a file says:
  - every HEADER record, user-defined ones included;
  - every DATA section with its parameters;
  - a complex instance of one part, kept apart from a simple instance;
  - the ANCHOR, REFERENCE and SIGNATURE sections, as text.

  The pin merges sections, drops the header records it does not know, and cannot write.
- **Typed errors.** `P21Error` has three cases: `Refused(Refusal)`, `Unsupported(Unsupported)`
  and `Cancelled`. A `Refusal` is `Syntax` (with its line), `Limit`, or `Entity { id, cause }`.
  Each layer is reachable through `source()`. The pin returns `Error(String)`.
- **Warnings are typed and returned** in `Parsed::warnings`, never printed. They are:
  - `DuplicateId`;
  - `SkippedHeaderRecord`;
  - `UnsupportedCodePage`;
  - `TextAfterEnd`.

  `protocol::Doubt` takes the place of the pin's warning `String`. Its `Display` gives the pin's
  exact words.
- **Units.** Lengths are in millimetres and angles in radians. Points and vectors are `[f64; 3]`
  and `[f64; 2]`. `scx-num`'s vector and point types are being changed by another builder, and
  the record should not depend on them in any case.
- **Edition 2021 throughout.** The pin's let-chains are rewritten as nested matches.

## 3. Decisions (analysis, then adversarial analysis)

1. **Read leniently, write strictly.** The reader accepts what real files contain:
   - lower-case keywords;
   - a space inside `# 1`;
   - lower-case hexadecimal in a binary;
   - text after `END-ISO-10303-21;`;
   - a byte-order mark;
   - a HEADER with no `ENDSEC`.

   The writer emits only what the §5.5 grammar allows. It refuses anything that cannot come
   back the same (`Unwritable`):
   - a non-finite real;
   - a keyword that is not a §6.3 keyword;
   - a typed parameter whose value is itself unwritable.

   Against: a lenient reader lets bad files pass silently. Answer: each accepted irregularity
   that changes meaning is a warning, and none of them is ambiguous.
2. **A typed parameter holds exactly one value** (§5.5 `TYPED_PARAMETER = KEYWORD "(" PARAMETER
   ")"`). The pin holds a list, and accepts `B()` and `B(1,2)`. We refuse both as syntax errors.
   Against: some writer might emit them. Answer: no file in the corpus does (section 4), and
   reading them as a list would give them a meaning the standard does not.
3. **A non-finite real**, such as `1.E400` overflowing to infinity, is read as the file gives it.
   The accessors (`as_f64`) give `None`, as the pin's do, and the writer refuses it. Refusing it
   on read would lose files whose overflowing value is never used.
4. **A code page.** `\PA\` to `\PI\` select ISO 8859-1 to 8859-9 for the `\S\` directives that
   follow (§6.4.3.3). Part 1 (Latin-1) is decoded. Any other part is read as Latin-1 with an
   `UnsupportedCodePage` warning, since its tables would be a dependency or a large constant.
   The pin does not decode `\P` at all: it keeps `'\PA\\S\a'` as its raw text.
5. **Repeated ids.** Within one DATA section the first definition is kept, and the repeat is
   dropped with a `DuplicateId` warning, as in the pin. Across sections both instances are kept,
   because §11.1 gives each section its own schema, and both are warned. `Exchange::get` finds
   the first.
6. **An empty complex instance**, `#1=();`, is a syntax error (§5.5 `SUBSUPER_RECORD = "("
   SIMPLE_RECORD_LIST ")"`, and the list has at least one record). The pin accepts it as an
   entity with no records.
7. **Enumerations are upper case** with digits and `_` only (§6.4.5). `.A-B.` is refused, as in
   the pin.
8. **Units default silently.** A context with no readable unit reads as millimetres and radians,
   as in the pin. A warning would be better. It is left for `scx-step`, which knows whether the
   context is used.
9. **Line numbers.** An error's line is counted from the nearest place already counted, forward
   or backward. The pin's `Lexer::line` counts again from byte 0 whenever the position moves
   back, which makes skipping many bad header records quadratic. This is a pin performance defect
   only; the line numbers it gives are the same.
10. **Limits scale with the file.** Records, parameters and memory are capped by density (16
    bytes per record, 4 bytes per parameter) as well as by absolute caps. A hostile small file
    therefore cannot claim huge counts. Progress is checked at the first instance and every 4,096
    after that.

## 4. Truth checks, then the pin

Truth comes first. Every test cites its clause.

- `tests/grammar.rs`, 23 tests:
  - reals, strings and every control directive, binaries, enumerations, typed parameters,
    complex instances and comments;
  - several sections, anchor, reference and signature;
  - text after the end, a BOM, short names, header skipping;
  - hostile nesting and sizes;
  - the error chain, limits, memory and progress.
- `tests/round_trip.rs`, 6 tests:
  - every parameter form;
  - the writer's refusals and its sharing of identical instances;
  - 300 generated exchanges;
  - every corpus file, read, written and read back equal, then written again to the same bytes.
- 15 unit tests (text, writer), plus 7 in `protocol`.

The pin comparison is a smoke detector, run outside the workspace (section 7).

No instance is present in one reader and missing from the other.

**35 hand-written edge cases:**

- 23 read the same in both readers.
- 6 are refused by both: unterminated comment, missing `;`, trailing comma, an id, an integer
  or a real out of range.
- 6 differ. In each, scx follows the clause and the pin does not:

| Case | scx | Pin | Truth |
|---|---|---|---|
| `#1=();` | refused | an entity with no records | §5.5: at least one record. Pin defect |
| `A(B(1,2))` | refused | typed with two values | §5.5 `TYPED_PARAMETER`: one parameter. Pin defect |
| `A(B())` | refused | typed with none | the same. Pin defect |
| `.A-B.` | refused | accepted | §6.4.5: no `-` in an enumeration. Pin defect |
| `'\PA\\S\a'` | `á` | the raw text | §6.4.3.3: `\S\` after `\PA\` is Latin-1 `0xE1`. Pin defect |
| `"0f"` | `0F` | `0f` | §6.4.6 has upper-case hex only. Both readers are lenient; scx normalises so that the writer's output is valid |

These are not yet entries in `scx-difftest`'s `pin_defects.rs`. See section 7.

## 5. Performance

Parse only, release build, the 6.1 MB `nist_ftc_09_asme1_ap242-e1.stp`. Median of 15 runs,
interleaved, two rounds:

| Reader | Median | Throughput |
|---|---|---|
| Pin `p21::parse` | 39.5 ms | 155 MB/s |
| `scx_p21::parse` | 27.3 ms | 224 MB/s |

That is 1.45 times the pin's speed. It was not profiled. One visible difference is that scx
holds instances in a flat vector, sorted once, where the pin uses a `BTreeMap`.

`scx_p21::write` of the same file takes 27.5 ms. The pin cannot write.

There is no "before" for this crate. The baseline is the pin. No counters were committed.

## 7. For the owner to rule on

1. **The committed pin comparison.** The pin's reader is in `solidcore-record`, which depends on
   `serde_json`. `serde_json` is not in our `Cargo.lock`, so adding `solidcore-record` to
   `scx-difftest` adds an external crate to the lock file. It is a dev-dependency only, and
   `[external]` in `layers.txt` stays empty. Until that is ruled, the comparison above was run
   from a scratch crate outside the workspace, not committed. The pin defects of section 4 are
   recorded here, not in `pin_defects.rs`.
2. **`ErrorKind` has no `Cancelled` or `Unsupported`.** `scx_num::error::ErrorKind` has
   `InvalidInput`, `Degenerate`, `StageFailed` and `Failed`. Both `P21Error::Cancelled` and
   `P21Error::Unsupported` map to `Failed` for now. A caller cannot tell "stopped on request"
   from "broken" without matching the concrete type. The proposal is to add both kinds to
   `ErrorKind`.
