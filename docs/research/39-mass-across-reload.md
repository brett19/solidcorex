Base da240580a4, scratch branch `cache-massreload-m` (local a local worktree; server worktree on the build server still present, a second corpus run with the trim-strip experiment was running when this was written: output on the build server `~/mr-out2.jsonl`). At every `body_from_smlib_ordered` export (native.rs:93) the probe measures a copy of the live SMLib body (accuracy 1e-8, 11 values), rebuilds it from the record exactly as `Body::smlib()` does (`Brep::from_record(record, true)`), measures that, and runs the experiments below. 474 exports (418 distinct records; 356 of them, 329 distinct, were later rebuilt by the app: same numbers as the full set).

## 2. Cause (MEASURED where stated; the final decomposition is NOT complete)
Facts established:
- Not the mass sum order alone and not the geometry fields I could restore. Experiments (equal-to-rebuilt / equal-to-live counts of 474, 8 quantities unless said):
  - Live body measured with faces visited in the record's order: equals live in 301 (so face order alone moves 173 bodies, by the same last-bit amounts) but equals the rebuilt body in only 121. Order is a real contributor, not the whole cause. The record's face order differs from the live body's list order in 340 of 474 bodies (edges 395); the rebuilt body's own re-export is in identity order in 474 of 474.
  - Import arrays built straight to a body (no record adopt step): same bits as the rebuilt body in 468 (the 6 others are blend-definition bodies), so the arrays->body step is where the rebuilt value comes from.
  - Live body's own arrays (no record at all) built back: equals live in only 107, equals rebuilt in 281. So the flat-array build alone already changes the mass of ~77% of bodies, before any record is involved.
  - Restoring live's values onto the import arrays: body tolerance (equal in all 474 anyway), model box EXTENT (live box is grown by the tolerance, e.g. -35.00001..35.00001 against the vertex box -35..35: differs in 474, but restoring it changes the mass in only 8 bodies), edge tolerance, vertex tolerance, vertex position: change 8 bodies or fewer; analytic surface parameters (plane, cylinder, cone, sphere, torus origin/axes/radius): 63 bodies; curves 41; all together 73 bodies move, but even with all of them restored the mass equals the live mass in only 105 and equals the live-in-record-order mass in only 123. So the fields restored are not what accounts for most of the change.
  - Rebuilt via the ops form (`solidcore_ops::Body::from_record`): see item 3.
- Tight bounding box (used for the integration origin and scale): equal live vs rebuilt in 472 of 474.
- Field differences between the record of the live body (R1) and the record exported from the rebuilt body (R2), so same canonical order, by field (bodies / leaves / max abs): UV pcurves of plane/spline faces (points 246 bodies, 4915 leaves, homogeneous 115, knots 32), surface frames of planes (x_axis 158, y_axis 147, origin 119 with up to 105 mm shift along the plane, i.e. same plane re-derived with another origin/axes), face domains 118, circle/line frames 1e-16, cylinder radius 96 bodies (max 2e-11), u/v axes 1e-16, cone half angle 1e-15, spline face control points 17 bodies (1e-12), edge and vertex tolerance 2 bodies (6e-8, one 1.6e-3 relative). READ: `import.rs` `plane()` (about 585-615) re-normalises the axes, forms y = z x x, and recomputes the face range from the domain corners; `laid_out` takes each edge/vertex tolerance as max(own, body) (import.rs:~334, 345); EXTENT is recomputed from the vertex box (import.rs:~355).
- Not examined: the live body's UV trims against freshly built ones (report 37: 93.6% identical, 6% differ in last bits, 0.4% beyond 1e-9), the faceuse/shell/loop order inside the body, and per-face internal caches. INFERRED: these are the remaining candidates (the face integration runs on the UV trims, which the live body holds from earlier operations and the rebuilt body builds afresh from its edges). I added a trim-strip experiment (live copy with all UV trims deleted, then measured) to test exactly this; the run (`~/mr-out2.jsonl` on the build server, fields `m_live_notrims`, `m_live_notrims_recorder`, plus `m_live_clone2`, `m_live_reverse`, `m_live_direct`) had not finished when this report was cut, so the result is NOT in this report.

## 2b. Follow-up: trim-strip run, copy fidelity, order sensitivity, and `fins_joined_into_their_hub` (MEASURED, run 2 = `out2.jsonl`, 474 exports; fins = `fins.jsonl`)
Pairwise bit-identity of the 8 quantities (of 474):
- Copy fidelity: live vs clone of clone vs the live body measured directly: identical in 474 of 474. The copy step is not a factor (and measuring the live body itself does not differ from measuring its copy).
- Order sensitivity: live with the face list reversed equals live in only 94. Record order equals live in 301. So summation order alone changes the last bits of 380 bodies when reversed: the live-vs-rebuilt change (370 differ) is of the same kind and size as an arbitrary reorder of the face sum.
- Trims: deleting every UV trim of the live copy (so they are built afresh from the edges, as the rebuilt body does) changes the live mass in 327 bodies (identical 147; relative change <=1e-15: 237, <=1e-12: 44, <=1e-9: 43, >1e-9: 3). So the live body's trims differ in value from fresh ones and the mass depends on that. But the stripped live body equals the rebuilt body in only 86 (live itself: 104), and stripped plus record order in 97. So trims, face order and the restored geometry classes each move the answer at the last-bit level, and none of them, singly or as order+trims, makes live equal rebuilt. Answer to the coordinator's question (1): NOT accounted for by trims; trim values are one of several last-bit contributors.
- INFERRED: the remainder is the same rounding sensitivity (the integrator's adaptive refinement under 1e-8) acting on a body whose internal state is built differently (topology build order, loop and edge order, trim values); nothing here shows a geometric difference.

`fins_joined_into_their_hub` (the 5e-7 body, 8 faces, all B-spline surfaces, body/edge tolerance 2e-5):
- Its record is a fixed point (R1 == R2), and every body built from arrays (live arrays, import arrays, restore-all) and the ops form give the same volume 278.1045515436817 bit for bit; only the live body gives 278.1046829948353. So no record field differs from what the live body exports: it is a state of the live body not carried by its arrays/record (its own surfaces' internal parameterisation and trims), not a field of the rebuilt body.
- Per-face areas agree to 1e-14 (one face to 4e-9) between live and rebuilt, so the surfaces and trims bound the same area. The per-face volume terms of the mass sum differ hugely (term 0: 128.485 vs 84.883; term 14: 30.314 vs 73.922) but cancel: they carry the closure strips of the integration (#16735), which are chosen per face and cancel across neighbours. The residual is 1.3e-4 mm^3 of 278 mm^3, with the faces carrying the closure terms (the face 7 mate term -3.5e-8 vs -5.4e-5, the faces 0 and 14 terms) the places it appears.
- Within the entities' tolerances? INFERRED yes: a 1.3e-4 mm^3 volume change over 543.5 mm^2 of surface is an average normal shift of 2.4e-7 mm, 80 times under the 2e-5 tolerance. It is also 50 times the integrator's requested 1e-8 accuracy, so it is the integrator's error on this body (closure strips on ruled B-spline faces), not a proved geometry change; I did not run an independent volume check. Not proved either way.

## 3. The two rebuild paths (MEASURED)
- SMLib form (`Body::smlib()`, what the app measures): above. 
- Ops form (`solidcore_ops::Body::from_record` then its `mass_properties`): vs live, all 11 identical in 6 of 474 and 8 quantities in 18; vs the SMLib rebuild identical in 19 (8 quantities 43). Volume vs live: 0: 214, <=1e-15: 230, <=1e-12: 29, larger 1. Area vs live: 0: 312, <=1e-15: 160, <=1e-9: 2. The two rebuilds therefore do not agree with each other bit-for-bit (they use different integrators, "estimated" in ops), but agree to 1e-12 on the 8 quantities in 83+ bodies and to <1e-9 in most; products differ more (see normalisation caveat).

## 4. Round-trip drift (MEASURED, 5 further trips on all 474, which includes the 20 worst)
- The record is NOT a fixed point after one trip: R1 == R2 in 86 of 474 (18%). The next records then settle (all later records equal) in 226 more; 154 bodies never settle in 6 exports (each export differs from the one before; pcurve points/knots and plane frames are what keeps changing).
- Mass does not drift in size: first vs sixth rebuild differ by at most 1.1e-14 (worst-of-8 normalised) over 5 trips, identical bits in 442 of 474; it wanders at the last-bit level (e.g. volume 1137.8521954092353, ...284, ...314, ...266, ...248, ...225 for one body) rather than growing or settling. Mass after trip 1 vs trip 0 differs in 32 bodies; later trips change 72-73 bodies each. Per-trip 8-quantity identity with the live value: 104, 104, 112, 104, 110, 101 of 474.

## 5. What a user sees (READ)
- The app never measures the live kernel result. `Body::from_smlib_record` keeps no SMLib body (body.rs:786-792) and `measure_mass`/`measure` read `b.smlib()` (crates/kernel/src/measure.rs:~97-106), the form rebuilt from the record (body.rs:826 `Brep::from_record(&self.record, true)`). `ModelBody::measure` (crates/doc/src/eval.rs:362) calls it; the inspect command goes through `measure_body` (crates/engine/src/cmd/inspect.rs:237), assembly mass through `measure_mass` (crates/engine/src/cmd/mass_properties.rs:~250) for volume and centroid, while the inertia comes from the display mesh (`solidcraft_io::mass_properties`, mass_properties.rs:255, io lib.rs:1162), not from SMLib at all.
- Reopening: the saved model cache stores the record exactly (`encode_native_body`, native.rs:21-46: `Saved { solid: body.record().clone(), ...}`) and decode rebuilds the same body from it (native.rs:67-80); a fresh evaluation exports the same record again (deterministic). So session and reopen measure the same rebuilt body from the same record: what the user sees is self-consistent. The pre-record live value is never displayed. (The 8 quantities of a live-vs-rebuilt difference exist only inside the kernel call that makes the result.) INFERRED; I did not run a save/reopen comparison of displayed numbers.

## 6. Does it violate the stated guarantee? (READ + MEASURED)
- The sentence is the doc comment at body.rs:786-789: the export "is not exact to the bit (its parameters, radians, pcurves), so that body measures and operates a little differently from the record's import, and a body evaluated afresh would then differ from the same body read back from a file. Every operation starts from the record's import." `docs/architecture.md` has no such sentence in this tree (grep); `docs/kernel-smlib-history.md:21` says truck bodies reopen from the cache bit-identically.
- The guarantee as written is fresh evaluation == reopened file, both measured on the record's import. The measurements here do not contradict it (I did not test fresh evaluation vs cache reopen end to end); the comment itself says the live export body differs from the import. The 98-of-345 mismatch is exactly the difference the comment says it avoids by never keeping the live body: it is outside what the statement covers, as long as no code path measures the pre-record body. One exception for the maintainers: records that never reach a fixed point (154 of 474 never settled in 6 trips) mean a re-save of a re-opened design can write a different record than the one it opened, although the rebuilt mass moves only by ~1e-14.
